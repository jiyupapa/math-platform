#### ①-상세. 개인화 설계 — 3층 구조 (2026-07-08 확정)

> 원칙: **결정은 규칙 기반, 설명은 LLM, 데이터는 이미 있는 것 재사용.**

**1층 — 입장 진단: 배치 테스트 (규칙 기반)**

핵심: 추천 경로는 이미 그래프로 설계돼 있다(루트 README 8단계). 개인화 = 새 경로 생성이 아니라
**진단 결과로 그래프의 어떤 노드를 "이미 앎/보류"로 접을지** 결정하는 문제. 필요한 진단은 경로 분기점에 대응하는 관문 4개뿐:

| 관문 | 묻는 것 | 통과 시 효과 |
|---|---|---|
| 벡터·행렬곱 | 1부 전반 핵심 감각 | 1단계 건너뛰고 바로 2단계로 |
| 확률 기초 | 조건부 확률·분포 읽기 | 2단계 건너뛰고 바로 4부 추론편으로 |
| 미분 | 기울기·연쇄법칙 감각 | 2부를 압축 복습 모드로 |
| log 감각 | 5부 최대 장벽 (2부 7장) | 5부 진입 시 복습 안내 여부 |

- 관문당 2~3문항, 총 10문항 안팎, **5분 이내** (수포자는 긴 시험 자체가 이탈 요인). 기존 `Quiz` 컴포넌트 재사용.
- **자기보고 2~3문항**(수학 자신감 1~5점) 포함 → 그대로 ③의 "학습 전" 측정값이 됨 (진단 + 전후 그래프를 도구 하나로).
- 자신감도 경로에 반영: 지식이 있어도 자신감이 바닥이면 건너뛰기 대신 **"빠른 복습" 모드** 권장.

#### ①-저장소-확정. 플랫폼 방향 확정 → 모노레포 채택 (2026-07-09 확정)

**반전 트리거 — 사용자가 제시한 "바뀔 수 있는 부분" 4가지:**
① 6·7부 등 프로젝트 추가 · ② local Ollama → 원격 IP Ollama 대체 · ③ 사용자 관리(등록/수정/삭제) · ④ 사용자 인증(로그인/로그아웃).

**왜 결론이 바뀌나 — ③·④가 백엔드를 부른다:**
- 인증·유저 관리 = **백엔드(서버+DB) 필수.** 진도가 localStorage(브라우저) → **서버 per-user 저장**으로 이동(계정의 목적 = 기기 바뀌어도 진도 따라옴). → 각 부 `progress`/`review` 스토어가 localStorage→API 로 바뀜(**전 부 공통 변경**).
- 이 순간 이전 판단의 두 근거가 무력화됨: (a) "동일 origin localStorage" 제약이 **사라짐**(진도가 API로 가므로 origin 파티셔닝 무관), (b) "모노레포는 개발자 편의일 뿐"이 **거짓이 됨** — 백엔드↔프론트 **공유 타입**(User/Progress/DiagnosticResult)과 교차 관심사 변경(토큰 부착·API 클라이언트·스토어 교체)은 골든카피 복붙으로 관리 불가. "하나의 백엔드 + N개 프론트 + 공유 UI/타입" = 모노레포가 존재하는 이유.
- ①(부 증가)는 공유패키지의 한계비용을 0으로 만들어 이 방향을 강화. ②(원격 Ollama)는 설정 seam 하나 + 백엔드 프록시로 자연 흡수.

**결론: 모노레포 구조를 지금 채택.** 단 타임라인 분리:
- **구조**(모노레포 + `packages/shared`)는 **지금** — 부 5개일 때가 전환 최저비용(6·7부 태어나기 전).
- **백엔드**(인증·유저·진도 API·Ollama 프록시)는 **실제로 필요할 때** 추가. 구조 먼저, 서버 나중.
- **해커톤 데모(12월)는 그대로 정적 + localStorage + local Ollama 버전으로 시연** — 최저 리스크. 플랫폼 기능은 데모 대상 아님.

**지금 심을 두 seam (미래를 막지 않기 위해):**
1. Ollama URL 을 설정값으로 (local→remote 가 설정 변경으로 끝나게).
2. 진도 접근을 스토어 인터페이스 뒤로 (localStorage→API 전환이 챕터 전체가 아닌 스토어 구현 교체 하나로 끝나게).

#### ①-저장소-localStorage. 왜 저장소가 제품 방향에 종속되나 — localStorage 한계 분석 (2026-07-09)

각 부는 localStorage 키를 여러 개 사용(1부 기준): `la-progress-v1`(완료 슬러그) · `la-review-v1`(복습 북마크) · QuizSet별 `la-...` 키.
독립 repo로 운영 시 이 localStorage가 일으키는 문제를 정리 — "간과했던 지점"의 정체.

**localStorage의 두 철칙**: ① **origin**(scheme+host+port, 경로 무관) 단위로 격리 · ② 그 **브라우저·기기 안**에만 존재(서버 없음, 계정 무관).

| # | 문제 | 내용 | 해결책 | 성격 |
|---|---|---|---|---|
| A | origin 파티셔닝 | 앱을 서브도메인 등 다른 origin에 배포하면 포털이 각 부의 `la-progress-v1` 을 **아예 못 읽음**(바구니 분리). 2층 개인화 붕괴 | same-origin 하위경로 배포 | 관리 가능 |
| B | 한 바구니 공유 | same-origin이면 5개가 **단일 바구니 공유** → 키 겹치면 덮어씀. `la`/`tf`/`it` **접두사가 충돌 방지 목숨줄** | 접두사(이미 적용) | 관리 가능 |
| C | **기기 넘어 못 따라옴** | localStorage는 그 브라우저에만. 폰·다른 브라우저·캐시삭제·시크릿 시 **진도 소멸.** localStorage = 계정이 아니라 익명 기기별 메모 | **서버 per-user 저장(백엔드)** | **localStorage로 해결 불가 — 구조적 천장** |
| D | dev 포트 분리 | `npm run dev` 는 포트가 5173/5174…로 달라 **다른 origin** → 같은 PC에서도 2층 재현 불가. "dev는 되는데 포털에 진도 안 뜸"에 속기 쉬움 | 단일 프록시 / 빌드본 검증 | 관리 가능 |
| E | 숨은 repo 간 계약 | 포털이 각 부의 키명·값포맷을 하드코딩해야 함. 부가 키를 바꾸면 **조용히 깨짐**(공유 타입 없음, drift도 못 잡음) | 공유 타입(모노레포) | 구조로 해결 |
| F | 내구성 | ~5MB를 전 앱이 공유, Safari ITP는 7일 미방문 시 삭제, 저장압박 시 축출. **영속 보장 없음** | 서버 저장 | 서버로 해결 |

**핵심**: A·B·D·E는 배포·접두사·타입으로 넘길 수 있는 불편. 그러나 **C는 localStorage의 구조적 천장**이고, 요구 ③·④(인증·유저 관리)가 정확히 그 천장을 뚫으라고 요구 → 진도가 서버로 가야 함 → 백엔드 → 모노레포. **저번 반전의 기술적 뿌리 = "localStorage는 계정을 흉내 낼 수 없다"(문제 C).**
쿠키 우회(`Domain=.example.com` 서브도메인 공유)? 4KB·매 요청 전송이라 진도용 부적합, 기기도 못 넘음 → 결국 same-origin(임시방편) 아니면 백엔드(정공법)로 수렴.

## 4. 확정된 결정사항

- **부 번호는 그대로 둔다** (4부 트랜스포머 ↔ 5부 정보이론 교체 안 함).
  - 5부는 "4부를 이미 본 사람" 전제로 설계됨(설계 원리: 수학은 쓰이는 곳을 본 직후/직전 배치).
  - "완결" 역할은 6부(LLM 조련)가 담당. 4부는 시리즈 중간의 보상 지점.
  - 번호 교체는 콘텐츠 곳곳의 상호 참조("4부 12장" 등)·디렉토리·드리프트 스크립트 연쇄 수정을 유발.
- **"4부 = 정점" 표현은 포털 표현 계층에서**: 첫 화면을 1~5 목록이 아닌 **학습 경로 지도**(README mermaid)로,
  4부에 "🎯 정점" 배지. 부 나열 시 역할로 묶기: **토대(1·2·3) → 조립(4) → 본체(5) → 조련(6)**.
- **캡스톤 챕터(TODO_260628 ②) 별도 제작 불필요**: "4부 전체 조립(ch10)"이 이미 그 역할.
- 비선형 학습 경로는 결함이 아니라 **"AI 강사 추천" 엔진이 필요한 이유** — 데모 핵심 서사로 사용.
