## 1. 왜 이 프로젝트에 검색이 특히 잘 맞나

이 시리즈의 핵심 설계가 **"같은 수학이 여러 부에 재등장한다"**이다
(README `부 간 주요 연결 지점` 표 — 예: KL 발산 = 5부 5장·6부 6장·8부 8장,
조건부 확률·베이즈 = 3부 4장·6부 4장·11부 6장).

그래서 사용자의 가장 값진 질문은 *"이 개념 어느 부/장에서 다루지?"*인데,
지금은 그걸 알려면 README를 뒤지거나 12개 앱을 각각 열어야 한다.
**통합검색은 이 재등장 구조를 그대로 활용하는 기능**이라 부가기능이 아니라
시리즈 논리의 자연스러운 완성이다.

## 2. 아키텍처 제약이 방식을 결정한다

조사로 확인한 제약이 방식을 거의 정해준다.

- **12개가 각각 독립 SPA**(Vue 3 + Vite, `createWebHistory(BASE_URL)`)로,
  정적 사이트 하나로 배포된다: 포털 `/`, 각 부 `/partN/`, `deploy/_redirects`가 SPA 폴백
  (Cloudflare/Netlify류). → **백엔드가 없다.**
- 프로젝트 에토스 = **오프라인·결정적·비용 0·데이터 유출 0**(로컬 Ollama 튜터와 동일).

**귀결**: Algolia·Elasticsearch 같은 **서버형은 부적합.**
답은 **클라이언트 사이드 검색 + 빌드 타임 생성 JSON 인덱스**.
정적 배포·무비용 원칙에 그대로 맞고, "검증 = `npm run build`" 모델에도
결정적으로 재생성돼 들어맞는다.

## 3. 권장 구성

**⌘K 커맨드 팔레트를 `packages/ui`에 두고, 루트의 공유 인덱스 하나를 물게 한다.**

| 요소 | 권장 | 이유 |
|---|---|---|
| **엔진** | MiniSearch 또는 Fuse.js | 인덱스가 작아(≈130장) 무엇이든 즉시. **한국어는 부분일치/n-gram 기반이 필수** — 영어 stemming 토크나이저는 한글에서 헛돈다 (FlexSearch `tokenize:"full"`도 후보) |
| **UI 위치** | `packages/ui`의 `SearchPalette` 컴포넌트 (⌘K/Ctrl-K) | 컴포넌트 1벌·인덱스 1벌 → 전 부·포털에서 재사용. 공유 패키지 철학 그대로. `searchIndexUrl`은 provide/inject로 주입, 기본 `/search-index.json` |
| **딥링크** | 결과 = `{part, slug, hash?}` → `/{part}/ch/{slug}#{hash}` | 섹션 앵커 이미 동작 (part 라우터 `scrollBehavior`가 `to.hash`를 80px 오프셋 처리). 부 간 이동은 풀 페이지 로드지만 허용 범위 |
| **빌드** | `scripts/build-search-index.mjs`가 전 부 데이터 → `deploy/search-index.json` | 결정적 재생성, 빌드에 훅 |

### provide/inject 계약 (기존 패턴과 일치)
- 신규 키 `searchIndexUrl` — 각 앱 `main.ts`가 주입. 기본값 `/search-index.json`
  (각 부가 `/partN/` base라도 루트 절대경로라 어디서든 fetch 가능).
- 기존 키들(`storagePrefixKey`·`reviewApiKey`·`notebookResolverKey`)과 같은 방식.

## 4. 무엇을 인덱싱하나 — 3단계, 1+2단계부터 권장

### 1단계. 메타데이터 (필수·저위험)
각 부 `apps/*/web/src/data/chapters.ts`의 `{part, slug, title, summary, notebook, advanced, phase}`.
- 이미 깨끗한 단일 소스, **`.vue` 파싱 불필요.**
- 이것만으로도 "X를 다루는 장" 내비게이션이 된다. ≈130 엔트리.

### 2단계. 개념·용어 + 동의어 레이어 (최고 가치) ★
- **README `부 간 주요 연결 지점` 표**가 이미 손으로 만든 "개념→위치" 지도라
  그대로 인덱스로 변환 가능.
- **비유어 앵커링** 때문에 필수: 사용자가 "파인튜닝"을 쳤을 때 제목이 "조련"인
  6부가 나와야 한다. 동의어 사전 없이는 **검색어≠제목**인 경우를 놓친다.
  예: 조련 ↔ post-training·파인튜닝·정렬 / 고무줄 자 ↔ 부동소수점 / 보폭 ↔ 학습률 /
  검수자 ↔ verifier / 몸집과 밥의 황금비 ↔ Chinchilla.
- 각 부 CLAUDE.md·README의 "비유어 앵커" 절이 동의어 사전의 원천.

### 3단계. 섹션 단위 풀텍스트 (선택·나중)
- 빌드 시 `.vue`에서 `<h2>`/`ConceptCard` 제목만 추출 → 섹션(#앵커) 딥링크.
- **1+2가 부족할 때만** 착수.
- **본문 전체 추출은 비권장** — `.vue` 템플릿이 KaTeX·인터랙티브 props와 뒤섞여
  파싱이 취약하고, 헤딩 대비 한계효용이 낮다.
- **선행 작업: 앵커 커버리지 정비 (2026-07-14 정밀 확인 — 이게 3단계 보류의 실제 이유).**
  라우터는 `to.hash`를 처리하고, `ReviewFlag`(`packages/ui`)가 `<span :id="..." class="scroll-mt-24">`로
  **id + 읽기 좋은 label + 스크롤 오프셋까지 완비된 섹션 앵커**를 이미 렌더한다. 즉 *메커니즘*과
  *추출원*(ReviewFlag 호출 파싱 — prose 파싱 아님)은 깔끔하다. **문제는 커버리지가 부마다 갈린다는 것**:
  - **part1~5: 287개 앵커(완비)** — `<h2>` 섹션마다 `<ReviewFlag id="chN-sM" label="...">`.
  - **part6~11: 0개(전무)** — 최신 부들이 ReviewFlag를 쓰지 않는다.
  - 이 상태로 3단계를 넣으면 **UX가 쪼개진다**(3부 개념은 섹션으로 점프, 8부 개념은 챕터 맨 위로만).
    균일한 챕터 단위보다 나빠서, 전 부 균일 섹션 딥링크는 **6~11부 ~67개 챕터에 앵커를 먼저 심는
    콘텐츠 패스**가 선행돼야 한다.

### 8-1. 3단계(섹션 딥링크) 보류 결정 (2026-07-14)

앵커 인프라를 정밀 확인한 결과 **현재 챕터 단위 유지(아래 선택지 A)**로 결정. 근거는 §4 3단계 각주 —

  균일하지만 별도 콘텐츠 작업. **3단계를 되살리려면 이 경로.**

## 9. 후속 — 개념 사전의 승격 (2026-09-06)

`scripts/search-concepts.json`(개념 65·위치 97)은 **개념 온톨로지 정본 `scripts/ontology/concepts.json`** 으로
승격·이전됐다(옛 파일 삭제). 형식이 바뀌었다 — 개념마다 정의처(`definedAt`)·회수처(`usedAt`+`how`)·선수(`prereq`)·
비유어(`metaphors`, 부 정보 포함)·섹션 앵커가 붙는다. `build-search-index.mjs` 는 새 정본을 읽고 **출력 형식은 유지**
(팔레트 무변경) — 개념 엔트리는 위치마다 하나(448 항목), 회수처 엔트리의 summary 에 "다시 쓰는 곳 — how" 가 들어간다.
검사기 `npm run check:ontology` 가 위치·앵커 실재를 커밋 전에 보장한다. 설계와 다음 단계(팔레트 "관련 개념" 확장 등):
`docs/todo_온톨로지_260906.md`.
